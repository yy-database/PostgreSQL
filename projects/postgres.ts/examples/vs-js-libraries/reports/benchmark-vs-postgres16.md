# 服务端对服务端：`@yydb/postgres` 与真实 PostgreSQL 16

真实库：`PostgreSQL 16.15, compiled by Visual C++ build 1944, 64-bit`（`127.0.0.1:35432`，库 `postgres`）
本仓：`@yydb/postgres`（每轮新起子进程服务与临时数据目录）
说明：truth corpus 的 SQL 差分基线来自 pglite 0.5.15；本机装有 PostgreSQL 16.15，这次直接用真实服务端。CI 有 `postgres:16` 时用 `BENCH_REAL_*` 指向该实例重跑。
轮次：1 轮热身 + 5 轮测量，取中位数并记 p95；数据集 1000 行，固定 seed。
比值 = 本仓耗时 / 真实库耗时，小于 1 表示本仓更快。
口径：`connect` 一项真实库每次都做认证与初始化握手，本仓连接是极简实现，两者不可比，该行不能当作性能结论。
口径：`order-limit` 在双方都先建同一条 `(val DESC, id)` 索引，测的是有序索引扫描加 `LIMIT` 提前停止，不是无索引内存排序。
口径：本次采样期间同机其他任务占满 CPU（整体利用率 100%），两侧绝对值同时抬高约 1.7~2 倍；只可比同轮倍数，不要与上一轮绝对值直接对照。

## 根因假设与预计收益

- **每语句固定地板**：`baseline-select1` 本仓 0.313ms/语句，真库 0.128ms。地板本身不高，差距主要来自读路径。
- **点查走索引**：`point-pk` 0.672ms/语句、`point-uk` 0.761ms/语句，扣掉地板后为 0.359ms 与 0.448ms，剩余是索引条目解码与逐行过滤的固定成本，不再随行数整表扫描。
- **范围与有序访问走索引、排序与分组仍整表扫**：`range-limit` 1.658ms/语句按索引区间取 20 行后逐行过滤；`order-limit` 1.645ms/语句在双方同建的 `(val DESC, id)` 上做有序索引扫描，取够 `LIMIT` 即停，不再整表排序；`group-by` 12.70ms/语句，`grp` 没有索引，仍整表扫描后聚合。
- **写入成本集中在每次提交的落盘**：`insert-single` 10.968ms/语句，比真库多 10.5ms；`tx-commit` 摊到 1.852ms/行，说明单条插入把整次提交的落盘成本整笔付一次。同机真实库保持默认 `synchronous_commit=on`，口径一致。
- **条件更新与删除同样是扫描加逐行改写**：`update-many` 0.510ms/行、`delete-many` 0.185ms/行。
